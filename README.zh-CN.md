# codex-cost

这是一个我自己很想要的小工具，因为我经常遇到一个问题：

> **Codex 的额度到底花哪去了？**

Codex 会告诉你 5 小时和每周额度用了多少，但它不会解释为什么这次掉得特别快。

codex-cost 会读取本地 Codex session，尝试把额度消耗拆成：

- 新增输入
- 输出和推理
- 每次请求本身的固定开销

然后再告诉你，如果同样的工作换一个模型，大概会是什么量级。

它平时待在 MacBook 刘海旁边。没有刘海的 Mac 会自动放到菜单栏。

- 原生 Swift
- 零依赖
- 不用注册账号
- 没有遥测
- 数据不出本机

## 安装

~~~bash
git clone https://github.com/kongleiwork-art/codex-cost
cd codex-cost
./build.sh
open CodexCost.app
~~~

只需要 Xcode Command Line Tools：

~~~bash
xcode-select --install
~~~

目前应用没有签名，所以第一次打开时需要右键 CodexCost.app，选择 **打开**，再确认一次。

如果想强制使用菜单栏模式：

~~~bash
open CodexCost.app --args --menubar
~~~

## 它能看到什么

收起时，它只在刘海旁边显示当前模型和额度水位，不怎么占地方。

点开以后可以看到：

- 5 小时额度
- 每周额度
- 当前燃烧速度
- token 构成
- 最近主要用了哪些模型
- 同样这些工作换成其它模型，大概会消耗多少额度

5 小时额度达到 80% 和 95% 时，它会提醒你。如果换一个便宜模型确实可能省下明显额度，也会顺手给一个建议。

它不是想告诉你“永远用最便宜的模型”，只是把以前看不见的消耗摊开给你看。

## 为什么做这个

我最开始只是觉得 Codex 的 5 小时额度有时候掉得特别快。

但只看一个百分比，很难知道到底是谁在烧额度：

- 上下文太长？
- reasoning 开太高？
- 输出太多？
- 小请求太频繁？
- 换了模型？
- cache 没命中？

所以我干脆自己测。

目前这套模型来自 **23 个实验组、421 次受控调用**，每次尽量只改一个变量。原始数据和实验脚本都放在 [research/](research/) 里。

先说明一下：**这不是 OpenAI 官方的计费公式。**

它只是我在 2026 年 9 月，用一个 Plus 账号实际测出来的结果。后续计量规则变了，数字也可能跟着变。

---

## 我目前测到的几个结论

### 1. Cached input 基本不怎么吃额度

在我的实验里，cached input 没有表现出明显的额度消耗。

所以一个已经带着 22 万 token 上下文的长 session，每一轮不一定会比 4 万 token 的 session 贵很多。只要大部分上下文还在 cache 里，真正重新付出的主要是最新那一小段输入。

所以**不要只是为了省额度就随手清 context**。重新读回来，反而可能更贵。

### 2. 很小的请求也有固定开销

在 gpt-5.6-sol 上，我测到每次请求大约有 **0.0667%** 的固定消耗。

也就是说，就算每次只返回一点点内容，差不多 15 次请求也可能吃掉 5 小时窗口的 1%。

这也是为什么一些重复 tool call、无意义的小循环，看着不大，累计起来却很疼。

### 3. Sol 的 reasoning effort 没看到额外倍率

在 gpt-5.6-sol 上，提高 reasoning effort 确实会更耗额度，但主要原因是它生成了更多 reasoning token。

我没有测到“High 本身再额外乘一个价格倍率”这种现象。

五档 effort 的实验结果都在 **1.0 ± 0.1** 左右。

所以从这批数据看，与其很早就跳到更贵的模型，不如先试试把 Sol 的 reasoning 往上调。

### 4. Astra 不能只用一个倍率来形容

Astra 是这次实验里最有意思的一个。

它的 input、output/reasoning 和每次请求固定开销，相对 Sol 的倍率并不一样。

所以“Astra 是 Sol 的几倍”这种说法其实很容易误导。

短而明确的 Astra 任务还算可控，但如果让它输出很长、持续推理，额度会掉得非常快。

## 实测系数

我没有给每个模型硬套一个总倍率，而是拆成三个部分：

| 模型 | 1% 可买的新增输入 | 1% 可买的输出 + 推理 | 每次请求 |
|---|---:|---:|---:|
| gpt-5.6-sol | 41,398 tok | 15,450 tok | 0.0667% |
| gpt-5.5 | 48,137 tok | 17,965 tok | 0.0574% |
| gpt-5.6-terra | 46,000 tok | 17,167 tok | 0.0600% |
| gpt-5.6-luna | 免费 | 免费 | 免费 |
| gpt-6-astra | 15,415 tok | 2,495 tok | 0.3514% |

在这批数据里，Astra 三部分相对 Sol 大约是 **2.7× / 6× / 5.3×**。

所以同样叫一次 Astra 调用，如果输入多、输出少，和输入少、输出特别长，最终消耗可以差很多。

## 这些数字有多准？

还有不少误差，所以我更愿意把它当“实测参考”，而不是账单。

- **Token 数是估算的。** 来自本地 session / tool output，不是 OpenAI 官方账单 token。
- **额度只有整数百分比。** 如果一次实验只让额度变化 3% 或 4%，舍入误差会很明显。
- **额度读数是事件驱动的。** Codex 发请求时才会写新值，所以最后一条记录可能已经过期。CodexCost 会结合 resets_at 判断，避免窗口已经滚过去了还显示旧的 99%。
- **5 小时额度看起来是滚动窗口。** 实际数据里出现过短时间从高位快速掉到 0% 的情况，更像一批旧用量一起过期。
- **Sol 的样本目前最扎实。** 22 个实验组，按请求回归的 R² 是 0.987。
- **5.5 和 Terra 暂时和 Sol 拉不开明显差距。** 当前误差范围有重叠。
- **Astra 和 Luna 样本更少。** 更适合看量级，不适合把小数点当真。
- **全部数据都来自一个 Plus 账号，时间是 2026 年 9 月。** OpenAI 改规则以后，需要重新测。

research/ 里保留了实验框架和 control 组，可以自己复测。

还有一点容易误会：

**这是订阅额度，不是 API 账单。**

少用一些 token 不会直接退钱，它真正带来的好处是让 5 小时和每周额度更耐用。

## 隐私

只读取本地的 ~/.codex/sessions。

不会上传 prompt、代码、文件内容，也没有遥测。界面里显示的只有聚合后的使用数据。
